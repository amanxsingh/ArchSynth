## 1. End-to-End Methodology Flow

The research methodology of ArchSynth v2.0 is systematically divided into six rigorous phases:

```mermaid
flowchart LR
    A[1. Repository Ingestion & Provenance] --> B[2. Domain-Specific AST Extraction]
    B --> C[3. Hierarchical Launch & Profile Resolution]
    C --> D[4. Communication & QoS Topology Recovery]
    D --> E[5. Schema-Constrained Multi-View Synthesis]
    E --> F[6. Empirical Benchmarking & Validation]
```

---

## 2. Phase-by-Phase Methodological Details

### 2.1 Ingestion & Provenance Control
- **Input Grounding**: Target repositories are pinned to exact Git commit SHAs. No analysis is conducted on floating or untagged branches.
- **Package Manifest Validation**: ArchSynth scans root and child directories for ROS 2 `package.xml` files. If zero package manifests exist, the pipeline halts immediately, preventing execution on non-ROS repositories (negative specificity control).
- **Artifact Provenance Attachment**: Every generated JSON document receives a `.provenance.json` sidecar capturing the repository name, commit hash, remote URL, local path, and analysis timestamp.

### 2.2 AST Parsing & Static Node Discovery
- **Python Codebases**:
  - Implements a custom `ast.NodeVisitor` that traverses the Python Abstract Syntax Tree.
  - Identifies class declarations inheriting from `rclpy.node.Node`.
  - Extracts node names initialized via `super().__init__('node_name')` or direct constructor parameters.
  - Traverses methods to locate `create_publisher`, `create_subscription`, `create_service`, and `create_client` calls.
- **C++ Codebases**:
  - Employs Clang-based AST parsing and heuristic symbol analysis.
  - Scans for classes subclassing `rclcpp::Node` and `rclcpp_lifecycle::LifecycleNode`.
  - Parses CMakeLists.txt to identify `add_executable`, `add_library`, and `rclcpp_components_register_node` targets.
  - Captures exact file paths and 1-based line ranges for every discovered node.

### 2.3 Symbolic Launch Hierarchy Resolution
- **Nested Execution Trees**: Recursively evaluates `IncludeLaunchDescription` directives, capturing parent-to-child launch dependencies.
- **Launch Substitutions**: Symbolically evaluates ROS 2 launch substitutions:
  - `LaunchConfiguration(name, default)`: Resolves default arguments and remappings.
  - `PythonExpression(expr)`: Evaluates conditional logic inside launch files.
  - `PathJoinSubstitution(parts)`: Resolves filesystem paths across packages.
- **Component Container Resolution**: Detects `ComposableNodeContainer` instances and dynamically maps contained components loaded via `LoadComposableNodes`.
- **Deployment Profiles**: Aggregates launch arguments and conditional branches into distinct deployment profiles (e.g., standalone execution vs. composable container loading vs. simulation).

### 2.4 Interface Extraction & Communication Graph Recovery
- **Interface Signatures**: Extracts topic, service, and action names along with their fully qualified message types (e.g. `sensor_msgs/msg/LaserScan`, `nav2_msgs/action/NavigateToPose`).
- **QoS Profile Deduction**: Extracts Reliability (`RELIABLE` vs `BEST_EFFORT`), Durability (`VOLATILE` vs `TRANSIENT_LOCAL`), History (`KEEP_LAST` vs `KEEP_ALL`), and Depth parameters.
- **DDS Endpoint Decomposition**: Accurately accounts for hidden node and endpoint expansions:
  - Coordinate Transforms: A `TransformListener` spawns a dedicated internal node (`transform_listener_impl_...`) that subscribes to `/tf` (`VOLATILE`) and `/tf_static` (`TRANSIENT_LOCAL`).
  - Interactive Markers: Inspects exact upstream library source (`interactive_markers` 2.5.5) to avoid false-positive legacy ROS 1 topic counts.
- **Boundary Role Classification**:
  - `SOURCE_CONFIRMED`: Interface declared directly in repository application code.
  - `DEPENDENCY_CONFIRMED`: Interface generated by upstream dependencies (`tf2_ros`, `interactive_markers`).
  - `INTERNAL_MATCHED`: Statically predicted intra-process communication counterpart.
  - `EXTERNAL_FACING`: Interface communicating with external system nodes or global frame trees.

### 2.5 Schema-Constrained Synthesis & Multi-View Generation
- **Subsystem Clustering**:
  - Builds an interaction frequency matrix $M_{ij}$ between all recovered nodes.
  - Computes Newman's graph modularity $Q$ to identify natural cluster boundaries.
  - Prompts the LLM (Gemini 2.5 Flash / local Ollama) using Pydantic v2 schemas to assign semantic labels, descriptions, and cohesion rationales to each cluster.
- **8 ISO/IEC/IEEE 42010 Architecture Views**:
  - Context View (Level 1 System Context)
  - Functional View (Decomposition into capabilities)
  - Component View (Level 3 C4 diagram)
  - Deployment View (Level 4 Container & process mapping)
  - Lifecycle View (LifecycleNode state machine transitions)
  - Communication View (Topic pub/sub & service interaction topology)
  - Plugin View (pluginlib base class interfaces and implementations)
  - Behavior Tree View (BehaviorTree navigation decision tree)

### 2.6 Validation and Benchmarking
- **Evidence Validator (`src/evidence_validator.py`)**: Traverses generated models, opening physical source files on disk to confirm that the claimed file exists and that the claimed line numbers contain the specified ROS 2 declaration.
- **Ground Truth Comparison**: Computes Precision, Recall, F1, and ARI against expert reference specifications.

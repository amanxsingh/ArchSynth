01. Context & Motivation

The Architecture Decay Problem in ROS2 Robotics

Why modern robotics software systems urgently require automated static architecture recovery

DDS Topology Blindspot

01. Implicit DDS Communication

ROS2 nodes communicate via asynchronous publish/subscribe topics, services, and actions. These connections are instantiated dynamically at runtime without a single centralized manifest, making data flows invisible during manual inspection.

Inability to trace interfaces
Composition Opacity

02. Multi-Layer Launch Trees

Robotics pipelines use deeply nested Python (.launch.py) and XML launch files with conditional logic, dynamic namespaces, and topic remappings. Manually tracing which node launches with which topic is nearly impossible in large repos.

Complex nesting & remappings
Software Erosion

03. Documentation Rot

As robotics packages evolve, hand-written architecture diagrams become outdated within weeks. Over 80% of open-source ROS2 packages lack up-to-date architectural specifications, leading to severe architectural drift.

High maintenance barrier
02. Literature Review

Recent Breakthroughs & Related Work (2026)

Analyzing the two dominant but disconnected research tracks in software architecture recovery

Track 1: ROS2 Architecture Recovery

Benchat et al. (arXiv:2602.18644) & Briechle et al. (arXiv:2605.20055)

  • What they do: Use LLM agents to read ROS2 source code and launch files, reconstructing hierarchical architecture diagrams (nodes, topics, launch composition).
  • Methodology: AST extraction and prompt engineering to reconstruct computation graphs.
  • Critical Gap: They stop purely at the diagram/graph model. They do not produce polished, standards-based written developer documentation, and their accuracy degrades on complex launch compositions.
No written developer manuals produced
Track 2: General Software Documentation

CIAO — De Luca et al. (Accepted ICSA 2026 / arXiv:2604.08293)

  • What they do: LLM pipeline that turns generic GitHub software repositories into structured architectural documentation (ISO/IEC/IEEE 42010, C4 model).
  • Evaluation: Empirically validated with 22 professional software developers.
  • Critical Gap: Has zero concept of ROS2. It cannot parse launch files, DDS pub/sub topics, namespace remappings, node lifecycles, or action servers. Fails on robotics codebases.
Completely blind to robotics middleware

04. Research Gap & Novelty

The Research Gap & Academic Contribution

Synthesizing two disjoint paradigms into an empirical, defensible dissertation contribution

Three Critical Research Gaps
Gap 1: The Recovery-to-Documentation Chasm

Existing ROS2 tools stop at diagrams. Engineers need structured written manuals (ISO 42010 / C4) describing component roles, lifecycle behavior, and external hardware interfaces.

Gap 2: The Robotics Domain Void in SE Tools

Tools like CIAO assume monolithic OOP class structures. They are completely incapable of resolving asynchronous DDS pub/sub topologies and nested launch trees.

Gap 3: Unconstrained LLM Hallucinations

Prior tools rely on loose natural-language prompts. Without strict schema validation, LLMs frequently invent non-existent topics and connections.

The Novel Contribution

ArchSynth fuses ROS2-aware static recovery with ISO 42010 documentation generation.

ArchSynth bridges the gap by pairing deterministic AST parsing of ROS2 nodes and launch files with Pydantic schema blueprints.

This enables LLMs to cluster subsystems and generate both interactive C4 Mermaid diagrams and standards-compliant developer manuals with verified zero hallucination.

Citable, defensible dissertation contribution

08. Methodological Rigor

Deliberate Scoping & Boundary Definition

Ensuring high software engineering rigor and realistic part-time dissertation execution

Strictly In Scope (Academic Focus)
• Static Source & Launch AST Analysis: Deterministic extraction of ROS2 nodes and launch composition without execution overhead.
• Schema-Constrained Synthesis: Enforcing strict Pydantic blueprints to mathematically eliminate LLM hallucinations.
• Standards-Compliant Output (ISO 42010 / C4): Generating standardized written documentation and native Mermaid diagrams.
• Quantitative Benchmarking: Precision, Recall, and F1 scoring against hand-crafted ground truths.
Deliberately Out of Scope (Avoiding Drift)
• Physical Robot & Gazebo/RViz Sim: Physical hardware and simulation do not impact static architecture recovery.
• Live Runtime Tracing (rosbag2 / LTTng): Runtime tracing is deferred to future work; static analysis ensures 100% code coverage.
• Reinforcement Learning / Perception: Focus remains on robotics software engineering rather than algorithm training.
• Kubernetes / Container Orchestration: Focus is on the ROS2 computational graph itself.
